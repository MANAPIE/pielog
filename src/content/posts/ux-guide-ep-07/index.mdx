같은 화면을 보고도 세 직무는 서로 다른 문제를 발견하고, 그 셋은 대개 모두 맞다.

배달 앱의 이탈률이 올랐다는 대시보드를 기획자, 디자이너, 개발자가 함께 봅니다. 회의가 끝나면 기획자는 주문까지 7단계가 너무 많다고 하고, 디자이너는 결제 버튼이 화면 아래 가려진다고 하며, 개발자는 상품 목록 API가 평균 2.3초 걸린다고 합니다. 누가 틀린 것이 아니라 각자의 시점이 다른 것이고, 문제는 한 렌즈로 전체를 판단하려 할 때 생깁니다.

---

## 이 단계에서 풀어야 할 질문

[ep.06 리서치 방법의 지도](/ux-guide-ep-06/)에서 리서치 방법을 골랐다면, 그 결과를 읽는 사람이 누구인지에 따라 발견도 달라집니다. 가진 도구가 망치뿐이면 모든 것이 못으로 보이는데, 기획자와 디자이너, 개발자는 각자 다른 도구(퍼널, 화면, 로그)를 가지고 있기에 못 또한 모두에게 다르게 보입니다.

그래서 이번 편의 질문은 "세 직무는 같은 데이터에서 각각 무엇을 발견하고, 그 발견을 어떻게 합쳐 문제의 전체 모습을 보는가"입니다.

---

## 기획자의 렌즈: 구조와 흐름

기획자는 서비스의 전체 구조와 사용자의 이동 경로를 봅니다. 배달 앱 이탈 데이터에서 기획자가 발견하는 문제는 다음과 같습니다.

- 주문 완료까지 7단계를 거쳐야 하는데 3단계로 줄일 수 있지 않은지
- 쿠폰 적용 시점이 결제 직전이라 여기서 이탈이 급증하는데 쿠폰 노출을 앞당기면 어떨지
- 신규 사용자가 첫 주문 뒤 재방문하지 않는데 온보딩 이후 리텐션 장치가 없는 것은 아닌지

기획자의 도구에는 단계별 이탈률을 추적하는 **퍼널 분석(funnel analysis)**, 전체 경로의 구조적 문제를 찾는 유저 플로우 다이어그램, 어떤 문제가 매출에 직접 닿는지 잇는 지표 매핑이 있습니다.

강점은 개별 화면이 아니라 전체 여정의 맥락에서 문제를 보는 것이고, 맹점은 화면 안의 디테일과 기술적 제약을 간과하기 쉽다는 점입니다.

---

## 디자이너의 렌즈: 접점과 감정

디자이너는 사용자가 화면과 만나는 순간의 경험과 감정을 봅니다. 같은 데이터에서 디자이너가 발견하는 문제는 다음과 같습니다.

- 메뉴 카테고리 아이콘이 너무 비슷해서 구분이 안 되는 것
- 결제 버튼이 화면 하단에 가려져 스크롤해야 보이는 것
- 주문 완료 뒤 피드백이 약해서 성공했는지 불안한 것
- 에러 상태에서 사용자가 아무것도 할 수 없는 막다른 화면

디자이너의 도구에는 사용자가 어디서 막히는지 직접 보는 사용성 테스트, [ep.04 좋은 UX의 원칙](/ux-guide-ep-04/)의 원칙으로 화면을 점검하는 휴리스틱 평가, 같은 문제를 다른 서비스가 어떻게 풀었는지 보는 경쟁사 벤치마킹이 있습니다.

강점은 사용자가 실제로 보고 만지는 접점의 마찰을 섬세하게 잡는 것이고, 맹점은 비즈니스 우선순위나 구현 비용을 간과하기 쉽다는 점입니다.

---

## 개발자의 렌즈: 시스템과 데이터

개발자는 사용자가 보지 못하는 시스템의 동작과 성능에서 문제를 봅니다. 같은 데이터에서 개발자가 발견하는 문제는 다음과 같습니다.

- 상품 목록 API 응답이 평균 2.3초라 이 지연이 이탈 원인일 수 있는 것
- 결제 단계에서 500 에러가 전체 요청의 0.5%에서 발생하는 것
- 특정 구형 OS에서 레이아웃이 깨지는데 그 버전 사용자가 12%인 것
- 검색 인덱싱이 띄어쓰기에 민감해서 "떡볶이"와 "떡 볶이"가 다른 결과를 내는 것

개발자의 도구에는 성능 병목을 추적하는 **APM(application performance monitoring)**, 사용자가 마주치는 장애를 파악하는 에러 로그, 어떤 환경에서 경험이 저해되는지 보는 기기·브라우저별 호환성 데이터가 있습니다.

강점은 사용자가 원인을 알 수 없지만 경험에 직접 영향을 미치는 보이지 않는 문제를 잡는 것이고, 맹점은 기술적으로 흥미로운 문제에 끌려 사용자 영향이 큰 문제를 놓칠 수 있다는 점입니다.

![같은 이탈 데이터를 세 직무가 각자의 렌즈로 보는 다이어그램. 가운데 '배달 앱 이탈률 상승'이라는 데이터 카드가 있고, 그 아래로 세 렌즈가 나란히 놓여 있다. 기획자의 렌즈는 구조와 흐름으로 퍼널·유저 플로우·지표 매핑을 도구로 삼고 7단계 주문과 쿠폰 시점을 발견하며, 강점은 전체 여정, 맹점은 화면 디테일과 기술 제약이다. 디자이너의 렌즈는 접점과 감정으로 사용성 테스트·휴리스틱 평가·벤치마킹을 도구로 삼고 가려진 결제 버튼과 약한 완료 피드백을 발견하며, 강점은 접점의 마찰, 맹점은 우선순위와 구현 비용이다. 개발자의 렌즈는 시스템과 데이터로 APM·에러 로그·호환성 데이터를 도구로 삼고 2.3초 API와 0.5% 결제 에러를 발견하며, 강점은 보이지 않는 문제, 맹점은 사용자 영향의 크기다. 하단 캡션은 세 렌즈가 모두 맞고 모두 부분적이라고 적혀 있다.](ux-07-01-three-lenses.svg)

| 렌즈 | 보는 것 | 도구 | 강점 | 맹점 |
|---|---|---|---|---|
| 기획자 | 구조와 흐름 | 퍼널, 유저 플로우, 지표 매핑 | 전체 여정 | 화면 디테일, 기술 제약 |
| 디자이너 | 접점과 감정 | 사용성 테스트, 휴리스틱 평가, 벤치마킹 | 접점의 마찰 | 우선순위, 구현 비용 |
| 개발자 | 시스템과 데이터 | APM, 에러 로그, 호환성 데이터 | 보이지 않는 문제 | 사용자 영향의 크기 |

## 세 시선이 합쳐지는 순간

세 렌즈가 한 문제 위에 겹치면 해결 순서까지 보이게 됩니다. "주문 완료 페이지에서 사용자 만족도가 낮다"는 문제를 예로 들면 다음과 같습니다.

**기획자**: 주문 완료 뒤 예상 배달 시간이 불분명하고, 실시간 추적으로 이어지는 연결이 없다는 것을 발견합니다.

**디자이너**: 완료 화면의 시각적 피드백이 약해서 성공했는지 실패했는지 시각적으로 구분되지 않는다는 것을 발견합니다.

**개발자**: 배달 예상 시간 API가 불안정해서 시간을 표시하지 못하고 있고, API 안정화가 선행되어야 한다는 것을 발견합니다.

세 발견이 모두 맞고, 해결 순서는 세 시선을 합쳐야 나옵니다. 개발이 API를 안정화하고, 기획이 예상 시간 표시와 실시간 추적 연결을 요구사항에 넣고, 디자인이 완료 화면의 피드백을 강화하는 순서입니다. 디자인만 먼저 고치면 표시할 시간이 없어서 화면이 비게 되고, 기획만 먼저 정하면 구현이 막히게 됩니다.

## 세 시선을 합치는 세 가지 방법

시선은 저절로 합쳐지지 않고, 크로스 팀 발견 세션, 문제 카드, 맹점 질문이라는 세 가지 장치가 필요합니다.

### 크로스 팀 발견 세션

같은 데이터를 세 직무가 한자리에서 보고, 각자 발견한 문제를 공유하는 세션입니다. 요령은 비판 없이 발산하는 시간을 먼저 갖고 그다음에 수렴하는 것입니다. 발산 단계에서 "그건 구현이 어려워요"나 "그건 우선순위가 낮아요"가 나오면 다른 직무는 말을 아끼게 되고, 그렇게 되면 세션은 가장 목소리 큰 렌즈 하나로 돌아갑니다. Marty Cagan은 프로덕트 매니저, 디자이너, 엔지니어 세 사람이 발견 단계부터 함께 움직이는 구성을 강조하는데, 이 세션이 그 구성을 회의 한 번에 압축한 형태입니다.

### 문제 카드

각 직무가 발견한 문제를 카드 한 장에 적습니다. 카드에는 세 가지를 기록합니다.

1. 문제가 무엇인가
2. 어떤 데이터나 관찰에서 발견했는가
3. 사용자에게 미치는 영향은 무엇인가

카드를 모아 비슷한 것끼리 묶으면 개별 직무에서는 보이지 않던 연결이 드러납니다. 디자이너의 "완료 피드백이 약하다"와 개발자의 "예상 시간 API가 불안정하다"는 따로 보면 다른 문제지만, 묶어 놓으면 같은 화면의 같은 원인에서 나온 문제로 읽히게 됩니다.

![문제 카드 템플릿과 클러스터링을 보여주는 다이어그램. 왼쪽에 문제 카드 템플릿이 있고 세 칸으로 나뉜다. 문제(무엇이 잘못됐는가), 근거(어떤 데이터나 관찰에서), 영향(사용자에게 미치는 것)이다. 오른쪽에는 세 직무가 쓴 카드 여섯 장이 두 묶음으로 클러스터링되어 있다. 첫 묶음 '주문 완료 화면'에는 기획자의 예상 배달 시간 불분명, 디자이너의 완료 피드백 약함, 개발자의 예상 시간 API 불안정 카드가 모여 있고, 둘째 묶음 '결제 단계'에는 기획자의 쿠폰 시점이 결제 직전, 디자이너의 결제 버튼 가려짐, 개발자의 결제 500 에러 0.5% 카드가 모여 있다. 하단 캡션은 따로 보면 다른 문제가 묶으면 같은 원인으로 읽힌다고 설명한다.](ux-07-02-problem-cards.svg)

### 맹점 질문

각 직무가 자기 렌즈의 맹점을 인정하고 다른 직무에게 적극적으로 묻는 습관입니다. 기획자는 개발자에게 "이 흐름에서 기술적으로 병목이 될 지점이 있나요"를, 디자이너는 기획자에게 "이 화면에서 사용자의 핵심 목표가 뭔가요"를, 개발자는 디자이너에게 "이 에러 상태에서 사용자에게 뭘 보여주면 좋을까요"를 물어야 합니다. 질문이 오가면 맹점이 서로 메워지고, 질문이 없으면 각자 자기 맹점 안에서 결정하게 됩니다.

## 기획자·디자이너·개발자가 각각 가져갈 것

**기획자**: 퍼널에서 이탈 지점을 찾았다면 그 지점의 화면을 디자이너와 함께 열어 보고, 그 지점의 응답 시간과 에러율을 개발자에게 물어야 합니다. 이탈 지점은 기획의 발견이지만 원인은 세 렌즈 어디에나 있을 수 있습니다.

**디자이너**: 사용성 테스트에서 참가자가 막힌 순간을 기록할 때 "왜 막혔는가"를 화면 안에서만 찾지 말고, 그 순간 로딩이 몇 초였는지와 그 단계가 흐름의 몇 번째였는지도 함께 적어야 합니다. 화면 밖의 원인이 화면 안의 증상으로 나타나는 경우가 많습니다.

**개발자**: APM에서 느린 API를 찾았다면 그 API가 어느 화면의 어느 순간에 호출되는지를 사용자 여정 위에 놓아 봐야 합니다. 같은 2.3초라도 첫 화면에서 그랬다면 이탈로 이어지고, 백그라운드 데이터 동기화면 느린지 아무도 모릅니다. 사용자 영향의 크기는 여정 위에 놓아야 보이게 됩니다.
