시안은 네트워크가 끊기지 않는 세계를 그리지만, 사용자는 인터넷이 끊기는 세계에서 그 화면을 사용한다.

시안대로 구현한 화면이 지하철에서는 로딩이 끝날 때까지 3초 동안 백지로 떠 있습니다. 검색창에 글자를 빠르게 입력하면 이전 검색어의 결과가 나중에 도착해 화면엔 과거의 잔상만 남고, 목록에서 항목을 지운 뒤 뒤로 가면 지우기 전 목록이 다시 보입니다. 손을 떨며 주문 버튼을 두 번 누른 사용자에게는 주문이 두 건 생깁니다. 네 문제 중 어느 것도 시안에 그려져 있지 않았고, 디자이너가 그릴 수 있는 것도 아니었습니다. 시안 밖에서 생기는 경험의 절반은 프론트엔드 코드가 결정합니다.

---

## 이 단계에서 풀어야 할 질문

[ep.15 세 시선: 디자인이 직무의 경계를 넘을 때](/ux-guide-ep-15/)까지 설계가 끝났다면, 이제 그 설계가 코드가 되는 단계입니다. 설계는 이상적인 조건을 전제하고 그려지지만, 코드는 느린 네트워크, 오래된 기기, 예상하지 못한 데이터, 버튼 연타 위에서 돌아갑니다. [ep.12 와이어프레임과 상태 설계](/ux-guide-ep-12/)에서 로딩·에러·빈 상태를 화면으로 그렸다면, 어느 조건에서 어느 상태로 가는지와 그 전환이 얼마나 빠른지는 구현이 정합니다.

그래서 이번 편의 질문은 "시안에 그려지지 않은 조건에서 경험을 어떻게 지키는가"입니다.

## 기능으로서의 속도

사용자가 느끼는 시간의 기준은 [ep.13 인터랙션 디자인의 원칙](/ux-guide-ep-13/)에서 본 Nielsen의 세 한계입니다. 0.1초 안에 반응하면 직접 조작하는 느낌이 유지되고, 1초까지는 사고의 흐름이 끊기지 않으며, 10초가 넘으면 주의가 다른 데로 갑니다. 이탈로 이어지는 시점은 그 사이에 있습니다. Google이 2017년에 SOASTA와 함께 발표한 모델에서는 모바일 페이지 로딩이 1초에서 3초로 늘면 이탈 확률이 32% 높아지고, 10초가 되면 123% 높아진다고 추정했습니다. 실측이 아니라 예측 모델이지만, 3초부터 이탈이 시작된다는 기준으로 널리 사용되고 있습니다.

속도를 하나의 숫자로 재지 않도록 Google은 **Core Web Vitals** 를 세 지표로 정의했습니다. Core Web Vitals는 실제 사용자 환경에서 측정한 로딩·반응·안정성 지표로, 검색 순위에도 반영됩니다.

| 지표 | 재는 것 | 좋음 기준 |
|---|---|---|
| LCP(Largest Contentful Paint) | 가장 큰 콘텐츠가 그려지기까지 걸린 시간 | 2.5초 이하 |
| INP(Interaction to Next Paint) | 탭이나 클릭 뒤 다음 화면이 그려지기까지 걸린 시간 | 200ms 이하 |
| CLS(Cumulative Layout Shift) | 로딩 중 레이아웃이 밀린 정도 | 0.1 이하 |

세 지표 모두 방문의 75번째 백분위수로 판정하므로, 평균이 괜찮게 나와도 느린 기기를 이용하는 사용자의 4분의 1이 기준에 못 미치면 통과하지 못합니다. 원래 첫 입력 지연(FID)이라는 지표가 있었는데, 2024년 3월에 INP로 대체되었습니다. 첫 탭만 재던 FID와 달리 INP는 방문 중 모든 상호작용의 반응을 재므로, 버튼을 누른 뒤 화면이 멈추는 문제도 밝힐 수 있습니다. 기준과 측정 방법은 [web.dev의 Core Web Vitals 문서](https://web.dev/articles/vitals)에 정리되어 있습니다.

![web.dev의 Core Web Vitals 문서 캡처. 세 지표가 카드로 나란히 있다. Largest Contentful Paint는 로딩 성능을 재며 페이지가 로드되기 시작한 뒤 2.5초 안에 일어나야 하고, Interaction to Next Paint는 상호작용성을 재며 200밀리초 이하여야 하며, Cumulative Layout Shift는 시각적 안정성을 재며 0.1 이하여야 한다고 적혀 있다. 각 카드에는 좋음·개선 필요·나쁨 구간이 녹색·주황·빨강 막대로 표시되어 있다.](ux-16-03-web-dev-core-web-vitals.png)

![사용자가 느끼는 시간의 기준을 0초부터 10초까지 한 줄의 시간 축에 놓은 다이어그램. 위쪽에는 Nielsen의 세 한계가 표시되어 있다. 0.1초는 직접 조작의 느낌이 유지되는 한계, 1초는 사고의 흐름이 끊기지 않는 한계, 10초는 주의가 머무는 한계다. 아래쪽에는 측정 기준이 표시되어 있다. 0.2초는 INP의 좋음 기준, 2.5초는 LCP의 좋음 기준, 3초는 Google 모델에서 이탈 확률이 32% 높아지는 시점, 10초는 123% 높아지는 시점이다. 하단 캡션은 사용자의 기준과 측정 기준이 같은 축 위에 있어 둘 중 어느 쪽을 넘겨도 이탈로 이어진다고 설명한다.](ux-16-01-time-limits.svg)

프론트엔드에서는 세 가지 종류의 개선을 할 수 있습니다.

**초기 로딩**: 첫 화면에 필요한 코드만 먼저 보내고 나머지는 나중에 받는 코드 스플리팅, 화면 밖 이미지를 나중에 받는 지연 로딩, 첫 화면의 스타일만 HTML에 넣는 중요 CSS 인라이닝이 있습니다. 셋 다 LCP를 줄입니다. 이미지에 크기를 미리 지정하면 로딩 중 레이아웃이 밀리지 않아 CLS도 함께 줄어듭니다.

**상호작용**: 화면은 초당 60번 그려지므로 한 프레임에 쓸 수 있는 시간은 약 16ms입니다. 탭에 반응해야 할 메인 스레드가 긴 계산이나 큰 목록 렌더링에 막혀 있으면 INP가 늘어나므로, 무거운 계산은 Web Worker로 옮기고, 화면에서 넘치는 긴 목록은 보이는 부분만 그려야 합니다.

**체감 속도**: 실제 시간을 줄일 수 없을 때는 기다리는 느낌을 줄입니다. 콘텐츠의 위치를 먼저 그리는 스켈레톤 화면과 서버 응답 전에 화면을 먼저 바꾸는 낙관적 UI가 있습니다. 사용자가 다음에 갈 가능성이 높은 페이지를 미리 받아 두는 프리페치도 여기에 들어갑니다. 스켈레톤과 낙관적 UI는 [ep.12 와이어프레임과 상태 설계](/ux-guide-ep-12/)와 [ep.13 인터랙션 디자인의 원칙](/ux-guide-ep-13/)에서 다루고 있습니다. 프리페치는 링크 위에 마우스를 올리거나 뷰포트에 들어온 링크를 미리 받는 방식이 흔하고, 모바일 데이터를 사용하는 사용자를 위해 받는 양을 제한해야 합니다.

## 상태가 어긋날 때 생기는 네 가지 문제

화면에 보이는 것과 서버에 있는 것이 다를 때 사용자는 잘못된 정보를 보고 행동하게 됩니다. 원인은 대부분 네 가지 중 하나입니다. 항목마다 화면에서 나타나는 모습과 대응 방법을 함께 적습니다.

- **경쟁 조건(race condition)**: 요청을 보낸 순서와 응답이 도착하는 순서가 다를 때 생깁니다. 검색창에 "ap"를 치고 바로 "app"을 쳤는데 "app"의 응답이 먼저 오고 "ap"의 응답이 나중에 오면 화면에는 "ap"의 결과가 남습니다. 새 요청을 보낼 때 이전 요청을 취소하거나(`AbortController`), 요청마다 번호를 붙여 마지막 번호의 응답만 화면에 반영해야 합니다. 데이터 요청 라이브러리는 대개 요청 키 단위로 이 처리를 해줍니다.
- **캐시 불일치**: 화면이 들고 있는 복사본이 서버와 달라질 때 생깁니다. 목록에 캐시를 사용했을 때, 항목을 지운 뒤 목록으로 돌아가면 남은 지우기 전 목록이 그대로 보입니다. 데이터를 바꾼 뒤에는 관련 캐시를 무효화해야 하고, 화면을 다시 열 때는 캐시를 먼저 보여준 뒤 서버에서 다시 받아 바꾸는 stale-while-revalidate 방식이 흔합니다. 이 이름은 2010년 HTTP 캐시 확장 표준(RFC 5861)에서 왔고, 지금은 프론트엔드 데이터 라이브러리의 기본 동작이 되었습니다.
- **무한 로딩**: 응답이 영영 오지 않는데 스피너만 도는 상태입니다. 터널에서 네트워크가 끊기면 요청은 실패도 성공도 하지 않습니다. 요청마다 타임아웃을 두고, 시간이 지나면 실패 상태로 바꿔 재시도 버튼을 보여줘야 합니다. 자동 재시도를 하더라도 간격을 점점 늘리고 횟수를 제한해야 서버 부하를 줄일 수 있습니다.
- **깜빡임**: 판정이 끝나기 전의 화면이 먼저 보였다가 바뀌는 상태입니다. 로그인 여부를 확인하는 0.3초 동안 비로그인 화면이 먼저 그려졌다가 로그인 화면으로 바뀌는 경우도 있습니다. 판정이 끝나기 전에는 어느 쪽도 아닌 중립 상태(스켈레톤)를 보여주거나, 서버에서 판정을 끝내고 올바른 화면을 내려보내야 합니다.

![경쟁 조건이 생기는 과정과 막는 방법을 두 단으로 비교한 다이어그램. 왼쪽 '취소하지 않을 때'에서는 사용자가 'ap'를 입력해 요청 1이 나가고, 곧이어 'app'을 입력해 요청 2가 나간다. 응답 2가 먼저 도착해 'app' 결과가 보였다가, 응답 1이 나중에 도착해 화면이 'ap' 결과로 덮인다. 마지막 상태는 입력은 'app'인데 결과는 'ap'이다. 오른쪽 '이전 요청을 취소할 때'에서는 'app'을 입력하는 순간 요청 1이 취소되고, 응답 2만 화면에 반영되어 입력과 결과가 'app'으로 일치한다. 두 단의 결론 문구는 같은 높이에 있다. 하단 캡션은 마지막으로 보낸 요청의 응답만 화면에 반영해야 한다고 설명한다.](ux-16-02-race-condition.svg)

네 가지 문제의 공통점은 테스트 환경에서는 거의 보이지 않는다는 것입니다. 개발자의 네트워크는 빠르고 데이터는 한정되어 있습니다. 그래서 브라우저 개발자 도구의 네트워크 제한(느린 3G)과 오프라인 모드를 켜고 주요 흐름을 한 번씩 돌아보면서 상태 버그를 찾아야 합니다.

## 에러가 보여줘야 할 것: 원인이 아닌 다음 행동

에러 상태를 화면으로 그리는 일은 [ep.12 와이어프레임과 상태 설계](/ux-guide-ep-12/)에서 다루고 있습니다. 구현에서 정해야 하는 것은 어떤 에러를 어떤 화면과 어떤 자동 처리로 연결하는지입니다. 에러는 원인에 따라 사용자가 할 수 있는 일이 다르므로, 원인별로 보여줄 것과 코드가 대신 할 일을 나눠야 합니다.

| 유형 | 원인 | 사용자에게 보여줄 것 | 코드가 대신 할 일 |
|---|---|---|---|
| 입력 에러 | 형식이 맞지 않는 입력 | 어느 필드가 왜 안 되는지, 어떻게 고치는지 | 입력 보존, 해당 필드로 포커스 |
| 네트워크 에러 | 연결 끊김, 타임아웃 | "인터넷 연결을 확인해 주세요"와 재시도 버튼 | 오프라인 감지, 연결되면 자동 재시도 |
| 서버 에러(5xx) | 서버 장애 | "잠시 후 다시 시도해 주세요" | 간격을 늘리며 자동 재시도, 횟수 제한 |
| 권한 에러(401/403) | 세션 만료, 권한 없음 | "다시 로그인해 주세요" 또는 접근 불가 안내 | 토큰 갱신 시도, 로그인 뒤 원래 화면으로 복귀 |
| 없는 리소스(404) | 삭제됐거나 잘못된 주소 | 대안 제시(홈, 검색, 비슷한 항목) | 비슷한 항목 추천 |

메시지의 문장은 Nielsen Norman Group이 2023년에 정리한 지침을 따르면 됩니다.

- 에러는 생긴 곳 가까이에 표시합니다.
- 색만이 아니라 아이콘과 텍스트로도 알립니다.
- 사람의 언어로 무엇이 문제인지를 정확하게 적습니다.
- 다음에 할 일을 제안합니다.
- 사용자를 탓하지 않는 긍정적인 어조를 유지합니다.
- 입력한 내용을 지우지 않습니다.

"잘못된 입력입니다"는 이 중 넷을 어깁니다. 어디가 잘못됐는지, 어떻게 고치는지가 없고, 사용자를 탓하며, 어느 필드인지도 알 수 없습니다. "전화번호는 숫자만 10자리에서 11자리로 입력해 주세요"로 바꾸면 넷이 한 번에 해결됩니다. 기술 코드(`ERR_CONNECTION_RESET`, `500 Internal Server Error`)는 로그에 남기고 화면에는 보여주지 않아야 합니다.

## 폼: 검증은 언제 하고, 제출은 어떻게 막는가

폼이라는 상호작용에서는 실패가 가장 자주 일어납니다. 검증을 언제 하느냐가 성공률을 좌우합니다. Luke Wroblewski는 2009년에 사용성 회사 Etre와 함께 22명에게 가입 폼 여섯 가지를 시험했습니다. 제출 뒤에만 검증하는 폼에 비해 인라인 검증 폼은 성공률이 22% 높고 오류가 22% 적었습니다. 만족도는 31% 높고, 완료 시간은 42% 짧고, 시선 고정(눈이 화면의 한 곳에 멈추는 횟수로, 적을수록 덜 헤맨 것)은 47% 적었습니다. 그런데 같은 연구에서 입력하는 도중에 검증하는 폼은 오히려 완료 시간을 늘렸습니다. 이메일의 "@"를 치기 전에 "올바른 이메일이 아닙니다"가 뜨기 때문입니다. 그래서 검증은 필드를 벗어날 때(blur) 하고, 아이디 중복이나 비밀번호 강도처럼 입력해 봐야 통과 여부를 알 수 있는 필드만 입력 중에 짧은 지연을 두고 검증하는 것이 낫습니다. Baymard Institute의 결제 폼 테스트에서도 입력 중에 오류를 띄우자 사용자가 멈추고 굳이 바로 하지 않아도 될 수정을 하기 시작했습니다. 올바르게 입력했을 때의 체크 표시도 피드백인데, 성공 표시는 사용자를 멈추게 하지 않으므로 입력 중에 보여줘도 됩니다.

제출 단계에서는 코드에서 이 세 가지를 구현해야 합니다.

- **중복 제출 방지**: 버튼을 누르는 순간 비활성으로 바꾸고 로딩 표시를 넣습니다. 그래도 네트워크 재시도나 새로고침으로 같은 요청이 두 번 갈 수 있으므로, 결제나 주문처럼 두 번 처리되면 안 되는 요청에는 요청마다 고유 키를 붙여 서버가 같은 키의 두 번째 요청을 무시하게 해야 합니다.
- **부분 실패 처리**: 서버가 여러 필드 중 일부만 거부하면, 첫 번째 오류 필드로 스크롤하고 포커스를 옮기며, 나머지 입력은 그대로 보존해야 합니다. 긴 폼에서 오류가 화면 밖에 있어 보이지 않으면 사용자는 버튼이 고장 났다고 생각합니다.
- **성공 뒤 동선**: 제출이 끝난 뒤 어디로 갈지를 정해야 합니다. 결과를 확인해야 하는 작업(주문)은 결과 화면으로 보내고, 반복되는 작업(댓글)은 그 화면에 머물며 토스트로 알리고 입력창을 비웁니다. 자동으로 이동한다면 이동 전에 성공을 알려야 "눌렀는데 사라졌다"는 느낌이 들지 않습니다.

## 기획자·디자이너·개발자가 각각 가져갈 것

**기획자**: 요구사항에 성능 기준을 숫자로 적어야 합니다. "빠르게"가 아니라 "LCP 2.5초 이하, 느린 3G에서도 첫 화면이 3초 안에"로 적으면 개발자가 측정할 수 있고 QA가 판정할 수 있습니다. 에러 메시지의 문구는 기획 산출물이므로, 원인별로 사용자에게 보여줄 문장을 화면설계서에 적어야 합니다.

**디자이너**: 로딩·에러·빈 상태를 그리는 일에 더해, 그 상태로 들어가는 조건과 머무는 시간을 개발자와 같이 정해야 합니다. 스켈레톤을 몇 초까지 보여주고 그 뒤에는 어떤 화면으로 바뀌는지, 재시도 버튼은 몇 번까지 보여주는지가 정해져 있지 않으면 구현마다 달라집니다. 폼의 성공 표시와 오류 표시를 색만으로 구분하지 않도록 아이콘과 문구를 같이 설계해야 합니다.

**개발자**: Core Web Vitals를 실제 사용자 데이터로 측정하고 75번째 백분위수를 보아야 합니다. 새 요청을 보낼 때 이전 요청을 취소하는지, 데이터를 바꾼 뒤 캐시를 무효화하는지, 모든 요청에 타임아웃이 있는지를 코드 리뷰의 기본 항목으로 두어야 합니다. 느린 3G와 오프라인 모드로 주요 흐름을 돌려 보는 일을 출시 전 점검에 넣으면 상태 버그 대부분을 출시 전에 찾을 수 있습니다.
